01 What this is

A group of friends share a handful of online accounts. Those accounts send verification codes to one address. This is the web app that receives them.

Two problems follow from sharing an address, and the design addresses them separately:

  • Collision. Two people signing in at once can't tell whose code is whose. Solved by a lock — one holder at a time, with a queue.
  • Exposure. A shared inbox shows everyone every code. Solved by ownership — each message is attributed to the person who held the box when it arrived, and only they can read the body.

Everyone can see that a message arrived, from whom, and who owns it. That transparency is deliberate: it means nobody can quietly reset the password on a shared account.

Threat model

This protects against accidental oversharing between people who trust each other, and it produces an audit trail. It does not defend against a malicious member — anyone in the Access policy can take the lock and trigger a password reset whenever they like. The Access policy membership list is the real security boundary. Keep it short.

02 Architecture

One Worker, one Durable Object instance, two entry paths. The DO is addressed as idFromName("mailbox") — a single global instance, which is what makes the lock correct without any locking code. Durable Object execution is serialised, so read-check-write on lock state cannot interleave.

Both entry paths converge on the same DO instance, so mail arrival and lock changes are ordered against each other by the runtime rather than by application code.

Why WebSockets rather than polling

With WebSocket Hibernation, ctx.getWebSockets() survives the DO being evicted from memory. That gives the central property of this design: a socket closing removes a participant, so there is no code path that leaves the lock held by someone who isn't connected. The classic stale-lock bug doesn't exist here, because "who holds the lock" is never stored as a fact that has to be kept true.

It also removes the need for an application heartbeat. Use ctx.setWebSocketAutoResponse() for ping/pong — the edge answers without waking the DO, so keep-alive costs nothing.

03 Identity and access

Identity is the email claim of the Cloudflare Access JWT. Never a client-supplied name — if the browser can assert who it is, anyone can steal or release the lock.

  1. Access application covers the entire hostname, including /api/* and the WebSocket upgrade path.
  2. Set workers_dev = false. A live *.workers.dev route bypasses Access completely and hands out the mailbox to the internet.
  3. The Worker independently verifies the Cf-Access-Jwt-Assertion header against the team JWKS at https://<team>.cloudflareaccess.com/cdn-cgi/access/certs, checking signature, exp, and that aud equals the application's AUD tag. Cache the JWKS in memory.

Step 3 is not redundant with step 1. It is defence in depth against a route that accidentally escapes the Access application.

Token expiry mid-session

The upgrade is authenticated once, but a socket can outlive the token. Store exp in the socket attachment; on any event, if now > exp, send {"t":"bye","reason":"token_expired"} and close. The client reconnects, passes through Access again, and — inside the reconnect grace window — keeps its queue position.

04 State model

The distinction that organises everything below: presence is derived from live sockets and never stored; ordering and timing are stored because they must outlast a hibernation cycle.

Persisted Derived Derived values are recomputed on every event. Never cache them across an await.

Persisted  Storage keys

seq          // number — monotonic counter, only ever incremented

participants // one small object, keyed by email
{
  "alice@example.com": {
    seq:        41,      // queue order, ascending = earlier
    wants:      true,    // clicked Request access
    lastSeenAt: 0        // ms; set when their socket count hits zero
  },
  ...
}

lock         // transition ledger — a record of *when*, not of *who currently*
{
  holder:     "alice@example.com" | null,
  acquiredAt: 1755300000000,
  prev:       { email: "bob@example.com", releasedAt: 1755299900000 } | null
}

lock is a cache of the derived holder plus the timestamps of the last handover. It exists solely so §07 can attribute a message that lands during a handoff. It is rewritten whenever recompute detects the holder changed — it is never read to decide who the holder is.

Derived  Per-socket, from the hibernation API

// at accept time
ctx.acceptWebSocket(server, [ `u:${email}` ])   // tag → ctx.getWebSockets(`u:${email}`)
ws.serializeAttachment({ email, connId, connectedAt, exp })

// anywhere, after hibernation
const liveEmails = new Set(
  ctx.getWebSockets().map(ws => ws.deserializeAttachment().email)
)

Tags are fixed at accept time, which suits us — a socket's email never changes. Grouping by email is what makes multi-tab work for free: three tabs from one person are three sockets, one participant, one queue position.

Persisted  SQL schema

CREATE TABLE IF NOT EXISTS messages (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  received_at    INTEGER NOT NULL,
  from_addr      TEXT    NOT NULL,
  to_addr        TEXT    NOT NULL,
  from_name      TEXT    NOT NULL DEFAULT '',   // display name, if the sender set one
  subject        TEXT    NOT NULL DEFAULT '',   // raw — owner only
  subject_masked TEXT    NOT NULL DEFAULT '',   // §08 — everyone else
  body_html      TEXT    NOT NULL DEFAULT '',   // sanitised, remote resources gone; text-only mail converted
  owner          TEXT,                          // immutable; NULL = shared with everyone for 10 min
  auth_pass      INTEGER NOT NULL DEFAULT 0     // SPF/DKIM/DMARC all passed
);
CREATE INDEX IF NOT EXISTS idx_messages_at ON messages(received_at DESC);

Ring buffer trim runs after each insert. Delete by rank, not by id > max - 100 — autoincrement leaves gaps and the arithmetic form silently deletes the wrong rows:

DELETE FROM messages
WHERE id NOT IN (SELECT id FROM messages ORDER BY id DESC LIMIT 100);

06 Lock lifecycle

One function computes the whole world. Call it at the end of every event — connect, close, request, release, alarm — then broadcast.

recompute(now)

live = { emails with ≥1 socket in ctx.getWebSockets() }

// 1. purge participants who are gone and past their grace
for (email, p) of participants:
    if !live.has(email) && now > p.lastSeenAt + RECONNECT_GRACE_MS:
        delete participants[email]

// 2. the lock and queue are just a sort
wanters = participants.filter(p => p.wants).sortBy(p => p.seq)
holder  = wanters[0] ?? null
queue   = wanters.slice(1)

// 3. record the transition, if any
if (holder?.email !== lock.holder):
    if (lock.holder) lock.prev = { email: lock.holder, releasedAt: now }
    lock.holder     = holder?.email ?? null
    lock.acquiredAt = now

// 4. queue pressure
if (holder && queue.length > 0):
    if (!deadline || deadline.email !== holder.email):
        deadline = { email: holder.email, expiresAt: now + QUEUE_PRESSURE_MS }
else:
    deadline = null

// 5. wake for whichever comes first
setAlarm(min(deadline?.expiresAt, graceExpiryOfAbsentHolder))
Why this is small

There is no acquire path and no release path. Requesting access sets a boolean; the sort decides the rest. The holder is wanters[0] and always has been.

Event handlers

EventAction before recompute
WS acceptIf participants[email] is absent, create it with seq = ++seq, wants = false. If present, leave seq untouched — this is what preserves position across a refresh.
requestwants = true, and seq = ++seq, so the queue is ordered by when people asked. Keeping the seq from when they first connected would rank by who opened the page first, and let an early arrival jump ahead of whoever holds the box.
releasewants = false. Valid whether holding or queued.
webSocketClose / webSocketErrorIf this was the participant's last socket, set lastSeenAt = now.
alarmIf deadline has expired and lock.holder === deadline.email: set that participant's wants = false, clear deadline, and send them {"t":"evict"}.

Eviction sets wants = false rather than moving the evicted user to the back of the queue. With two active people, auto-requeue rotates the box between them every three minutes forever, whether or not either is using it. Re-requesting is one click, and it lands them at the back because requesting assigns a fresh seq.

Concurrency

Read participants and lock, mutate, write — with no await on anything external in between. Durable Object input gating protects storage operations, but an await fetch() in the middle of a read-modify-write still opens a window for interleaving.

What happens without a queue

Nothing. An idle holder with a tab open keeps the box indefinitely, and that is correct — the cost of holding is zero while nobody wants it. The moment someone requests access, the three-minute clock starts. There is deliberately no maximum session length.

07 Mail intake and ownership

Worker email() handler

  1. Reject if message.from is not on ALLOWED_SENDERS. Drop silently; do not bounce, which would confirm the address exists.
  2. Read Authentication-Results from the headers. auth_pass = 1 only if SPF, DKIM and DMARC all pass.
  3. Extract plaintext (prefer text/plain; strip tags from text/html if that's all there is), truncate to BODY_MAX_BYTES.
  4. Sanitise the HTML part (below) and truncate to HTML_MAX_BYTES.
  5. Compute subject_masked (§08).
  6. Forward to the DO stub for attribution and insert.

The attribution problem

Ownership is assigned when a message arrives, but the act that caused it happened earlier — typically 2–30 seconds, occasionally minutes. The eviction mechanism makes this worse rather than better:

The race being solved

Alice holds the box and clicks "send me a code". Bob queues. Alice's three minutes expire and Bob becomes holder. Alice's code arrives five seconds later. Under naive attribution, Bob owns Alice's code and can read it — precisely the leak ownership exists to prevent.

Attribution rule

attribute(at T):
    // A handover is exactly when delivery lag misattributes mail.
    if lock.prev && (T - lock.prev.releasedAt) < HANDOFF_GRACE_MS:
        return lock.prev.email
    return lock.holder          // may be null

Four lines, covering every case: a settled holder owns their mail; a message landing seconds after a handover goes to the person who left; a message landing shortly after the last person released goes to them; anything else is unowned.

Ownership never changes

It is decided once, at insert, and the column is never updated. There is no claim, no transfer and no contest — which removes an entire protocol from the design, along with the two columns and the UI that went with it.

The grace window is deliberately short. It stood at 90 seconds while a claim button existed as an escape hatch; with ownership immutable there is no escape hatch, so it is sized to cover ordinary delivery lag (2–30 seconds) without stealing mail the incoming holder triggered themselves — which takes longer than 30 seconds to arrange.

Unowned mail is shared, for ten minutes

When owner is NULL, nobody held the box when the message arrived, so there is nobody to protect it from. It is readable in full by everyone, and its subject is not masked — masking exists to hide a code from people who are not its owner, and this message has none.

That lasts PUBLIC_WINDOW_MS (10 minutes) from arrival. After that it is locked for everyone: subject masked, body refused. A code nobody claimed in ten minutes is either used or stale, and leaving it open indefinitely only widens who can see it. Readability is computed on every read from received_at, so the lock holds the moment the window closes; an alarm at that moment re-sends the item to open tabs so the page catches up without a refresh.

That also fixes a failure the earlier design had: mail arriving while nobody was watching is no longer dead weight nobody can ever read. And the rule fits in one sentence — hold the box and you own what arrives; don't, and it belongs to everyone.

The case it gives up is a code triggered by someone who closes their laptop before it lands. The handover grace covers the first 30 seconds of that; past it, abandoning the box means giving up the claim. Re-triggering the code is always available.

Sanitising the HTML part

Bodies render as HTML, because a verification email stripped to plaintext often loses the button you actually needed. The rendered body runs in a sandboxed iframe with scripts disabled (§10), so this pass is defence in depth rather than the only line — but two of its jobs are its own.

  • Remote images are tracking pixels. Loading one tells the sender that a message arrived at your login-code mailbox was opened, when, and from what IP. Every remote src and srcset is removed outright, so the URL never even reaches the browser and there is nothing to opt into later. Inline data: images stay — they fetch nothing.
  • Links must survive. Magic links are half of what a temporary mailbox is for, so every <a> gets target="_blank" and rel="noopener noreferrer", and javascript:, vbscript:, data: and file: hrefs are dropped.

Everything scriptable or navigable is removed outright — script, iframe, object, embed, form and friends — along with every on* attribute. HTMLRewriter does the work: it is part of the Workers runtime, so this needs no dependency and no hand-rolled HTML parsing.

08 Subject masking

Verification mail routinely puts the code in the subject line:

123456 is your Netflix code
G-729481 is your Google verification code
Your Discord code: 483920
[Steam] 5XK2M is your login code

So "everyone sees titles, only the owner sees bodies" leaks the protected value in a large share of real cases. Mask any short alphanumeric run containing a digit:

const mask = s => s.replace(/\b(?=[A-Za-z0-9-]*\d)[A-Za-z0-9-]{4,10}\b/g, '••••••');

// "123456 is your Netflix code"  →  "•••••• is your Netflix code"
// "[Steam] 5XK2M is your login code"  →  "[Steam] •••••• is your login code"

Requiring at least one digit leaves ordinary words alone; the 4–10 character bound leaves "2FA" and years mostly intact while catching every common code format. It over-masks occasionally, which is the right direction to fail.

Non-negotiable

Masking happens in the Durable Object, before the value goes on the wire. Sending the raw subject and hiding it in the UI puts the code in a WebSocket frame that anyone can read from devtools. The raw subject column is serialised only for the owner.

09 WebSocket protocol

JSON frames, one t field for type. Everything runs over the single authenticated socket rather than a second HTTP API, so there is exactly one place where identity is established.

state

One roster rather than separate holder and queue fields. Everyone with the page open appears, including people who have not asked for the box — which is what lets the UI be a presence list and highlight your own row whatever your role.

Message metadata

{

  authPass: true
}

And the body, returned only to the owner:

{ t: "body", id, html }   // or { t: "body", id, denied: true }
One enforcement point

Lists never carry bodies. A body crosses the wire only in response to an explicit {t:"body", id}, checked at that moment against one condition — owner === you || (owner === null && now < received_at + PUBLIC_WINDOW_MS). An unreadable body is never serialised at all, rather than being filtered out of a bulk payload, so there is one place to get right and nothing for a later refactor to leak.

At 100 rows the archive needs no pagination; metadata for the whole table is a few tens of kilobytes. Build the per-recipient serialisation loop plainly and resist adding a compute-once-send-to-all fast path — with per-message ownership it would have to be unwound.

10 Client behaviour

  • Connect on load. Send {t:"ping"} every 30 s.
  • Reconnect with exponential backoff, capped around 10 s. Inside RECONNECT_GRACE_MS the queue position survives.
  • On pagehide, call ws.close(). This is a courtesy that frees the box a few seconds sooner — not a correctness mechanism. It will not fire on iOS Safari, on tab discard, or on a crash, and none of that matters, because the socket closing is what the server actually reacts to.
  • Render the countdown from deadline - now using the server's now. Warn visibly at WARN_AT_MS.
  • There is no session concept. One list, ordered by time. "New" is a client-side render decision: item.at > connectedAt gets highlighted, everything else renders as history. Storing a session boundary would break on every reconnect and every second tab.
  • The archive is available to anyone authenticated, in any role — the idle included. Gating it on queue membership would push people to press Request just to re-read an old code, taking a turn from someone who needs the box.
  • Unread arrivals while the tab is hidden show as a count in the document title. It clears on visibilitychange.
  • A message that arrives already owned by you opens itself. Only the newest, and only yours.

Rendering happens in place, never by rebuilding

Each message gets one DOM node, created once and patched thereafter. This is not a performance concern at a hundred rows — it is a correctness one. Rebuilding a list's innerHTML reparents its iframes, and reparenting an iframe reloads it, so every unrelated state change (someone joining the queue, a countdown tick) would blank and refetch every open message.

The same constraint shapes insertion order: new nodes are prepended and existing nodes are never moved, which works because arrivals are monotonic in time and the list is newest-first.

Message bodies

The rendered body goes in an iframe with sandbox="allow-popups allow-popups-to-escape-sandbox". Scripts, forms and same-origin access stay blocked; what is deliberately allowed is target="_blank" navigation, because magic links are half of what a temporary mailbox is for.

The frame is built from srcdoc with its own <meta> CSP fixed at img-src data: — the second of three layers, after the server-side rewrite (§07) and before the parent page's own policy. It is assigned once per message; reassigning reloads the frame and loses scroll position.

An opened message shows its exact arrival time beside the plain-text toggle. The list gives you 5m ago, which is what you want while scanning; the opened message gives the timestamp, which is what you want when judging whether a code is still current.

A fixed-height scrolling frame is a deliberate limitation: measuring content height would require running a script inside the frame, and no message body is worth that.

Mail that is not yours still opens

A locked message used to be inert — no cursor, no hover, nothing happened on click. That is the worst version of a refusal: it reads as broken rather than as deliberate, and it leaves the reader with no idea what to do next.

Every card opens now. An unreadable one opens onto two sentences instead of a body, over a large, very faint eye-with-a-slash watermark:

Received by bob@example.com, so only they can open it.       ╱╯
Request the mailbox, then trigger the email again — the new    (╱╯)
one will be yours. Or ask bob@example.com to share this one.     ╱╯

The watermark does the work the text cannot do fast enough. An expanded panel sits exactly where a message body would, so at a glance it reads as a very short email; the mark says this is not content before a word of it is read. It is set at 7% opacity of the primary ink, right-aligned and clear of the text, so it registers peripherally without ever competing to be read.

The second sentence changes with your own role — someone already holding the box is told to just trigger the email again, someone in the queue is told to wait for their turn first, and only someone idle is told to request it. Advice that ignores the state you are actually in is worse than none.

There is no button here. The action already exists on your own row in the roster, a few centimetres up the page, and a second copy of it inside a message would be the only place in the interface where the same command appears twice.

No body is requested for these. The client already knows the message is unreadable, so the explanation is built locally and the round trip never happens; the server's own refusal stays in place purely as a backstop for the case where ownership changed between the list arriving and the body being asked for.

The plain-text view

Not a fallback to be tolerated — for a lot of verification mail it is the better view, so it gets the same care as the rendered one.

  • Monospace, at a readable size. The usual argument for a proportional face is prose comfort, and it loses here: this is a mailbox for codes, and telling 0 from O and 1 from l matters more than paragraph rhythm. Monospace also preserves whatever indentation the sender used to set a code apart.
  • Full-strength ink. Message text is the content, not a caption, so it takes the primary text colour rather than the muted secondary one used for metadata.
  • URLs become links. Only absolute http(s) URLs match, which is what makes it safe without a sanitising pass — javascript: and data: can never be produced. Trailing sentence punctuation is trimmed off the href, so "visit https://x.example/verify." does not link the full stop.
  • Light tidying. Trailing spaces and runs of three or more blank lines collapse, which templated mail produces constantly.

What it deliberately does not do is highlight anything that looks like a code. That is the same guess §13 rejects for extraction, only quieter: a highlight on the wrong token still reads as "this is your code", and being wrong occasionally is worse than never claiming to know.

The presence list

One row per person, in one shape: avatar, address, status, and — for you alone — the single action available. Status is carried by colour, so the same row reads at a glance:

DotMeaningYour action
Solid greenHas the mailboxRelease
Solid amberWaiting, with queue positionExit
Solid greyHere, not askingRequest
Hollow greyAway — inside the reconnect grace—

Rows are split into three ungrouped cards — in use, waiting, idle — so the state of the box reads from the shape of the page before any row is read. There are no group headings: each row's own status says what it is, so a heading above it would only repeat that.

Status is written as a sentence with the address as its subject, so a row reads straight through — alice@example.com · is using the mailbox, or · is next in line. Your own row switches to the second person (You are using the mailbox), which is the one place the phrasing changes.

The address and the status sit on two lines rather than one, with the avatar beside them and the action button at the end. A full-sentence status and a long address would otherwise compete for the same horizontal space, and the row would break first on a phone — where it is most likely to be read. Stacking removes the breakpoint rather than moving it.

Only the first card keeps a placeholder when empty, because "No one is using the mailbox" is actionable: you can take it right now. An empty queue is an absence with nothing attached, so that card simply is not drawn, and neither is the countdown unless a clock is running.

Among the idle the current user sorts first, and their row carries a me badge alongside the highlight. The other two cards are never reordered — those carry queue position, and sorting them would misreport whose turn is next.

Connection state follows the same rule as everything else: nothing is shown while the socket is healthy, and a Reconnecting… bar appears when it is not. A permanent green dot confirming normality is noise, and removing it makes the abnormal case louder rather than quieter.

Sign-out is an outlined button in the top right, and it asks before acting. Signing back in is only a one-time PIN away, so the dialog is not there to prevent damage — it is there because the button sits near things people press all day, and an accidental sign-out is pure friction.

Three addresses, three lines

A message involves three addresses, and conflating them is the easiest way to make this UI confusing: the sender it came from, the address of ours it was delivered to, and the person it ended up belonging to. Each gets its own line, in that order:

Netflix  no-reply@netflix.com                    5m ago
•••••• is your Netflix code
to codes@example.com
received by bob@example.com

The third line is the one that decides access, so it says so in words rather than as a status chip. It reads received by you, received by bob@example.com, or received by no one · open to everyone for 7 more min, or, once that window has closed, received by no one · locked. The clause matters, because "no one" alone would read as locked when it means the opposite.

A yours badge sits at the right of that line when the message is yours. It duplicates the sentence, deliberately: the sentence is for reading and the badge is for scanning a list without reading any of it.

11 Security checklist

  • workers_dev = false in wrangler.toml.
  • Access application covers the whole hostname, including the upgrade path.
  • JWT signature, exp and aud verified in the Worker, independently of Access.
  • Identity taken from the JWT email claim only, never from a request body.
  • Socket closed once its recorded exp passes.
  • Subject masking applied in the DO, before serialisation.
  • Bodies served only on explicit request, only to owner.
  • Cache-Control: no-store on every non-static response.
  • Sender allow-list enforced in email(); non-matching mail dropped without a bounce.
  • SPF/DKIM/DMARC result surfaced in the UI — a spoofed "here's your code" is otherwise indistinguishable from a real one, and the whole point of this box is that people act on codes without thinking.
  • Ring buffer trim runs on every insert, so a spam flood cannot grow storage.
  • Restrictive Content-Security-Policy on the served HTML.
  • Access policy membership reviewed whenever someone leaves the group.

ALLOWED_SENDERS is a comma-separated list of domains and full addresses. It lives in config rather than in a UI: changing it is a ten-second redeploy, and there is no mutating endpoint to secure and no way for someone to widen it to * and forget.

Email Routing is configured in the dashboard: route the address to this Worker. The UI is a single HTML string served by the Worker — no Pages project and no build step.

13 Decided against

RejectedReason
HTTP polling with a leaseSuperseded by WebSockets. beforeunload is unreliable on iOS Safari, tab discard and crashes, so a lease would be the only real mechanism and every release would be a race.
Maximum session lengthAn idle holder costs nothing while the queue is empty, and queue pressure handles every case where it does cost something.
Auto-requeue after evictionTwo active people would trade the box every three minutes indefinitely.
Opening the page joins the queueA forgotten background tab would take a full turn on every rotation.
Deleting mail that arrives unownedDestroys codes during ordinary disconnects, and the service being signed into often rate-limits the retry.
A separate session boundary in storageBreaks on reconnects and second tabs. The client can derive "new" from its own connect time.
Claiming, transferring or contesting ownershipAttribution is decided once and never changes. The handover grace covers the case the claim protocol existed for, in four lines and with no UI, and unowned mail being readable by everyone removes the other reason to claim.
Hiding mail that nobody owns, on arrivalThere is no one to protect it from while it is fresh. It is hidden only after ten minutes, once it is no use to anyone.
A plain-text viewOne way to show a body. The occasional text-only message is converted to HTML on arrival, with its links kept.
Extracting the code from the messageHeuristics get it wrong often enough that a confidently displayed wrong code is worse than none — you copy it, it fails, and nothing tells you the app guessed. Rendering the message solves the same problem exactly.
Loading remote images, everEvery image in a marketing-templated email is a callback to the sender. An opt-in control was built and then removed: forwarded mail rewrites URLs often enough that it only half-worked, and "never" is both simpler and strictly more private than "not yet".
A frontend frameworkTab badge, new-message highlighting and auto-open are a few lines each. The rendering rewrite that iframes require is needed either way, and a build step is a real cost against a project whose deploy is one command.
Per-user addresses instead of a lockWould make ownership unambiguous and remove the queue entirely — but it does not apply here, because the accounts being shared are already registered to one fixed address.

Open, and fine to defer

  • A 24-hour TTL sweep on top of the ring buffer. Cheap, further reduces data at rest, needs the alarm to serve two purposes.
  • Letting an owner delete their own messages from the archive.
  • Auto-release when all of the holder's tabs have been hidden for a couple of minutes. Nice, but adds a visibility protocol for a case queue pressure already covers.
